# Issue Jump

Chrome extension (Manifest V3) that jumps to issues in Jira, GitHub, GitLab, Linear and custom trackers, from a popup, the address bar and the right-click menu.
Plain ES modules, HTML and CSS. No dependencies, no bundler, no build step: `extension/` ships exactly as written.

## Commands

```bash
npm test            # unit tests (node:test): core, providers, storage, service worker
npm run test:ui     # the popup driven in headless Chrome against the preview stub
npm run test:all    # both, plus check
npm run coverage    # unit tests with a coverage report
npm run check       # manifest, version sync, permission and store-policy checks
npm run preview     # popup in a browser tab with a fake chrome API and fake tracker data (port 8765)
npm run build       # dist/issue-jump-<version>.zip      (--dev variant: npm run build:dev)
npm run icons       # re-render PNG icons from extension/icons/icon.svg (needs rsvg-convert)
npm run screenshots # regenerate store images (needs Chrome and rsvg-convert)
npm run wiki:shots  # regenerate wiki screenshots in wiki/images (needs Chrome and Pillow)
```

Run `npm run test:all` before finishing any change.

## Tests

- `tests/core.test.mjs`: pure logic. Routing typed text to trackers, detection from tabs, migration, history import.
- `tests/providers.test.mjs`: each provider's network functions against canned responses (`globalThis.fetch` is replaced).
- `tests/storage.test.mjs`: settings, tokens and history against an in-memory `chrome.storage`.
- `tests/background.test.mjs`: the service worker's listeners, with a recording `chrome` stand-in.
- `tests/ui/cases.js`: the real popup in an iframe with `tools/preview/stub.js`, run by `tests/ui/run.mjs` in headless Chrome. Watch them at `/__tests/index.html` under `npm run preview`.

Every behaviour change needs a test at the lowest level that can see it: pure logic in `core`, API shapes in `providers`, anything on screen in `tests/ui/cases.js`. New screens or states need a scene in the stub and a UI case. A bug fix starts with a test that fails. Never loosen the hostile-data case (`scene=hostile`): tracker text must stay text.

## Layout

- `extension/lib/core.js`: shared by popup and service worker. Top half is pure and unit tested: `resolve()` turns typed text into issue references across trackers, `detectTrackers()` recognises trackers in tabs, `migrate()` upgrades old settings. Bottom half wraps `chrome.storage`, `chrome.tabs` and `chrome.permissions`.
- `extension/lib/providers/`: one module per tracker plus `index.js`, the registry. `docs/providers.md` documents the interface.
- `extension/lib/http.js`: `request()`, the only place `fetch` is called.
- `extension/popup.{html,css,js}`: the popup. Views switched by `data-view` on `#app`: `main`, `settings`, `add`, `tracker`. `popup.js` keeps one `state` object, `buildRows()` turns it into sections of rows, `render()` paints them. Tracker forms are generated from each provider's `fields`.
- `extension/background.js`: service worker for the omnibox keyword `j`, the context menu, and fetching summaries after the popup closes.
- `tools/preview/`: dev server plus `stub.js`, which fakes `chrome.*` and tracker APIs. Scenes via `?scene=default|single|empty|setup|signedout`, with `&tab=blank`, `&q=text`, `&view=settings|add|tracker`, `&found=1`.
- `wiki/`: source of the GitHub wiki (user documentation). `.github/workflows/wiki.yml` copies it to the wiki when `main` changes. `wiki/images/` is generated by `npm run wiki:shots`.
- `store/`: Chrome Web Store listing copy and images. `docs/releasing.md`: release and store setup.

## Data model

- A tracker is `{ id, type, enabled, ...provider fields }`. Trackers live in `chrome.storage.sync` under `trackers`; their tokens live in `chrome.storage.local` under `tokens` and are merged in by `getSettings()`. Save with `saveTrackers()`, never by writing `trackers` directly.
- An issue reference is `{ tracker, key, url }`. History entries add `summary`, `status`, `statusColor`, `pinned`, `ts`.
- Issues seen outside the extension (a provider's `recent()`, browser history) enter history through `mergeSeen()`, which never moves an issue back in time and skips ones the user removed (`hidden`) or cleared (`clearedAt`).
- `settings.numbersTo` is the tracker bare numbers go to. `settings.prefixes` maps a learned key prefix to a tracker id.

## Rules

- **No new dependencies or build tooling.** If something seems to need one, raise it instead.
- **Never pass text from a tracker, a web page or the user to `innerHTML`.** Use `textContent` or DOM methods. `innerHTML` is only used with the static `ICONS` strings in `popup.js`.
- **Network requests go only to a configured tracker's own host**, through `request()` in `lib/http.js`. No analytics, no other hosts, no remote code, no `eval`.
- **Trackers are added without asking only when `detect` returns `trusted: true`**, which is reserved for exact hostnames over HTTPS (`github.com`, `gitlab.com`, `linear.app`, a single `<name>.atlassian.net`). Anything self-hosted or ambiguous is a suggestion the user confirms. Never save a tracker taken from page content or a tab URL otherwise.
- **Tokens never go to `chrome.storage.sync`** and are sent only to the service they belong to.
- **Do not change permissions casually.** `scripts/check.mjs` pins them. A change must update `manifest.json`, `scripts/check.mjs`, `PRIVACY.md`, `store/listing.md` and the README table together. A new required permission is a major version bump; a new optional one, requested only when the user turns a feature on, is a minor bump.
- Browser history is read only in `seenInBrowser()`, only when `settings.useHistory` is on and the `history` permission is granted, and only pages a provider's `fromUrl` recognises are kept.
- Host access: `*.atlassian.net` is granted at install. Every other host is requested at runtime with `chrome.permissions.request`, which only works inside a user gesture (a click handler).
- Jumping must work without lookups: `provider.url()` never needs a network request or a token.
- Keep pure logic pure and add a test in `tests/core.test.mjs` for every parsing, routing, detection or URL change.
- Jira REST: use `api/2` paths so Server / Data Center keeps working. The one exception is `api/3/search/jql` for Cloud, with an `api/2/search` fallback.
- UI: neutral greys with one accent colour, few dividers (group with spacing and a small label instead), 13px system font, sentence case, short plain copy. Colours are CSS variables in `:root` with a dark-mode block; never hard-code a colour elsewhere. Check light and dark.
- The popup must stay fully usable from the keyboard: focus stays in the input, arrow keys move `state.sel`.
- No company-specific names, sites or project keys anywhere. Examples use `acme`, `ABC-123`, `WEB-12`.

## Documentation goes with the feature

Every commit that adds or changes something a user would notice must update the documentation in the same commit. Treat it as part of the feature, not a follow-up:

1. **Wiki** (`wiki/`): update the page that covers it. A new tracker gets its own page plus rows in `Trackers.md`, `Home.md`, `_Sidebar.md` and `Privacy-and-permissions.md`. A new setting goes in `Settings.md`. A new failure a user can hit goes in `Troubleshooting.md`.
2. **Screenshots**: embed them as `<img src="images/name.png" alt="…" width="400">`, never as markdown images (they are double-size captures). If the popup looks different, run `npm run wiki:shots`. For a new screen, add a `shot` line to `scripts/wiki-shots.sh` (and a scene to `tools/preview/stub.js` if needed) and use the image on the page.
3. **`CHANGELOG.md`**: a line under `## [Unreleased]`.
4. **`README.md`** when the feature list, the tracker table or the permission table changes; **`store/listing.md`** and `npm run screenshots` when the store description or screenshots would be out of date; **`PRIVACY.md`** when what is stored or sent changes.

Write the wiki for someone who has never seen the extension: what it does, the exact steps, what they will see. Never edit the wiki on GitHub directly; the workflow overwrites it from `wiki/`. `npm run check` fails on broken wiki links and missing images.

## Branches and releases

Both `dev` and `main` are locked. Nothing is pushed to either directly, by anyone; never try to bypass or relax the protection.

- **Every change starts on a feature branch** cut from `dev`: `feat/…`, `fix/…`, `docs/…`, `test/…`, `chore/…`, `ci/…`. Commit there, push the branch, and open a pull request to `dev`. Outside contributors do the same from a fork.
- **Pull requests to `dev`** need both required checks green: `check` (unit tests, popup tests, policy checks, build) and `description` (`scripts/check-pr.mjs`). Squash-merge, then delete the branch. One topic per pull request.
- **`main` changes only through a release pull request from `dev`**, with the same two checks. Use `.github/PULL_REQUEST_TEMPLATE/release.md`, title `Release X.Y.Z`, tick the checklist truthfully, merge with a merge commit.
- **Write a real description** on every pull request: under "What does this change?" say what users or the code get and why, and what deserves a close look; under "How did you test it?" say what was run, against which trackers, and what was not tested.
- User-visible changes get a line under `## [Unreleased]` in `CHANGELOG.md`.
- The version lives in both `extension/manifest.json` and `package.json`; they must match.
- Merging to `main` with a new version tags it, creates a GitHub release and publishes to the Chrome Web Store. Release tags (`v*`) cannot be moved or deleted.
- Commit subjects: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, `ci:`. Do not add AI attribution or co-author trailers to commits or pull requests.
